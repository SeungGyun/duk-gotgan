세 가지 일을 따로 돌립니다

처음에는 한 사이클이 검색부터 요약까지 다 했습니다. 그랬더니 앞이 막히면 뒤가 통째로 밀렸습니다 — 긴 영상 하나를 받아쓰는 동안 요약이 몇 시간씩 놀았습니다.

1분마다

검색

유튜브에서 후보를 찾고, 광고·홍보·너무 오래된 것을 룰로 거릅니다.

30초마다

자막

자막을 받습니다. 막히면 소리를 받아 맥 GPU 로 직접 받아씁니다.

1분마다

요약

5편이 모이거나 한 시간이 지나면 AI 를 한 번 부릅니다.

각 잡이 끝낼 때 다음 상태를 세워 둡니다. 서로를 기다리지 않고, 하나가 죽어도 나머지는 그대로 돕니다.

왜 이렇게 만들었는가

AI 는 영상 한 편당 한 번만 부릅니다

자막을 읽고 요약을 만들어 save_review 도구를 부르는 것으로 끝납니다. 그 도구의 구현체는 워커 프로세스 안에 있습니다 — AI 는 스키마에 맞는 값을 넘길 뿐 셸도 DB 도 만지지 않습니다. 남이 쓴 자막을 도구 가진 에이전트에 넣는 구조라, 능력이 아니라 인터페이스만 줍니다.

자막은 대개 직접 받아씁니다

유튜브 자막 API 가 IP 단위로 막히는 일이 잦습니다(429). 그래서 소리를 받아 맥의 GPU 로 받아씁니다 — mlx-whisper 의 large-v3-turbo, M4 실측 5~6배속. 자막 경로가 열려 있으면 그쪽을 먼저 씁니다.

사람이 늘어도 비용은 늘지 않습니다

영상 테이블의 기본키가 유튜브 영상 ID 라, 두 사람이 같은 주제를 걸어도 자막도 요약도 한 번입니다. 비용은 사람 수가 아니라 서로 다른 키워드 수에 비례합니다. 읽음·즐겨찾기·제외만 사람마다 따로 쌓입니다.

큐도 브로커도 없습니다

잡 사이의 배타 제어는 MySQL 의 GET_LOCK 으로 합니다. 한 대에서 프로세스가 셋뿐이라 Redis 를 하나 더 띄울 이유가 없었습니다. 16GB 기계에서 메모리가 진짜 병목이라, 안 띄우는 것이 이득입니다.

설치

애플 실리콘 맥 · 도커 · 유튜브 API 키(무료) · Claude Code 로그인이 필요합니다. 30분쯤 걸리고, 다 끝나면 로그인만 하면 알아서 도는 상태가 됩니다. 

git clone https://github.com/SeungGyun/duk-gotgan.git
cd duk-gotgan

cd backend  && docker compose up -d      # MySQL (3307)
uv sync --extra asr --extra dev
cp .env.example .env                     # 유튜브 키 한 줄만 채웁니다

cd ../frontend && npm install && npm run build

cd .. && ops/install.sh                  # 상시 기동 등록 (launchd)

자세한 것은 설치 매뉴얼에 있습니다 — 준비물부터 첫 키워드까지, 안 될 때 어디를 보는지까지.

집 공유기 안에서만 쓰는 전제로 만들어졌습니다. 비밀번호가 네 자리뿐이고 TLS 도 없습니다. 밖으로 열 목적이라면 이 설계로는 안 됩니다.
